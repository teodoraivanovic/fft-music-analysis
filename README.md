# FFT Music Analysis

**Pitch and harmony detection in audio signals using the Fourier transform**

Course project for Scientific Computing, Faculty of Mathematics, University of Belgrade

## Project description

The project goes from a raw audio signal to a recognized chord sequence, using Fourier analysis implemented from scratch. The pipeline is:

```
raw audio -> spectrum (DFT/FFT) -> time-frequency (STFT) -> pitch (F0) -> chromagram -> chords
```

The emphasis is on **numerics** - implementing the transforms ourselves, analyzing their complexity, and comparing methods experimentally - rather than on calling library functions.

What is implemented:

1. **DFT and FFT from scratch.** The naive DFT in O(n^2) (matrix form) and the Cooley-Tukey FFT in O(n log n), plus the inverse transform. Correctness is checked against `numpy.fft` and running times were compared.
2. **STFT and spectrogram.** Window functions (rectangular, Hann, Hamming, Blackman), spectral leakage, and the time-frequency resolution trade-off.
3. **Pitch detection.** Two methods are implemented and **compared**: autocorrelation (computed via the FFT using the Wiener–Khinchin theorem, with parabolic interpolation for sub-sample accuracy) and the Harmonic Product Spectrum (HPS). They were evaluated with MAE and RMSE.
4. **Chromagram and chord detection.** The spectrum is folded into 12 pitch classes, and chords are recognized by template matching (24 major/minor triads) using cosine similarity, and evaluated against ground truth.

## Dataset

The `data/` folder contains two`.wav` recordings:

| File | Sample rate | Duration | Samples | Used in |
|---|---|---|---|---|
| `piano.wav` | 44100 Hz | 5.05 s | 222,821 | notebooks 02, 03, 04 |
| `guitar.wav` | 44100 Hz | 5.05 s | 222,821 | demo |

They are mono after loading, and `load_wav()` normalizes amplitudes to [-1, 1] as `float64`. They come from the course exercise repository `NI-2025` (`05-furijeova-transformacija/data/`.

Because the problem is regression on frequency (not classification), the notion of class balance does not apply directly. Instead, the **synthetic signals** generated by `common.generate_tone()` and `common.generate_chord()` serve as the controlled evaluation set: they span MIDI notes 48-83 (C3-B5, 36 notes, one per semitone - a uniform sweep across the range) with a known ground-truth frequency, which is what makes MAE/RMSE meaningful. Real recordings are then used to show where the methods break down.

## Results

**FFT correctness.** The from-scratch DFT and FFT agree with `numpy.fft` to machine precision (max error ~1e-14), and `ifft(fft(x))` round-trips to ~1e-15.

**Pitch detection** on synthetic tones with harmonics and added noise
(36 notes, C3–B5):

| Method | MAE | RMSE |
|---|---|---|
| Autocorrelation (with parabolic interpolation) | 0.021 Hz | 0.032 Hz |
| HPS | 1.107 Hz | 1.365 Hz |

Autocorrelation is roughly 50x more accurate here, because it is not limited by the FFT bin resolution. HPS is coarser but is known for robustness to noise. Neither is universally better, which is why both are implemented and compared.

**Chord detection** on the synthetic I–vi–IV–V progression (C major => A minor => F major => G major): **100% accuracy**, mean cosine similarity ~0.97.

**Limits on real audio.** On `piano.wav`, the two pitch methods disagree (~96.8 Hz / G2 vs 220.0 Hz / A3). This is an octave-type error, made messier by the inharmonicity of real piano strings, and is discussed in notebook 03.

## Setup

Python 3.11+ is required for this project.

```bash
git clone <repository-url>
cd fft-music-analysis

python -m venv .venv
source .venv/bin/activate

pip install -r requirements.txt

jupyter notebook
```

After that open the notebooks in `notebooks/` in numerical order. Each notebook adds `../src` to `sys.path`, so run them from inside the `notebooks/` directory (which is what Jupyter does by default when you open a notebook from there).

Dependencies (`requirements.txt`): `numpy`, `scipy`, `matplotlib`, `jupyter`.
